# 3. What is `@Entity`?

An entity represents a database table in Java.

Example:

```java
@Entity
public class Order {

    @Id
    private Long id;

    private String productName;
    private double amount;
}
```

`@Entity` tells JPA:

> This Java class should be treated as a persistent database entity.

Conceptually:

```text
Java class
   ↓
Order
   ↓
Database representation
   ↓
orders table
```

# 4. What is `@Table`?

`@Table` allows us to explicitly specify the database table name.

Example:

```java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    private Long id;
}
```

This means:

```text
Java Entity       Database Table
     ↓                  ↓
   Order     →       orders
```

Without `@Table`, JPA/Hibernate can derive the table name using its naming strategy.

Using:

```java
@Table(name = "orders")
```

explicitly says:

> Use the `orders` table.

# 5. Why did `@Table(name = 'orders')` give an error?

Wrong:

```java
@Table(name = 'orders')
```

or:

```java
@Table(name = ''orders)
```

Java uses:

```text
' '    → char
" "    → String
```

For example:

```java
'o'
```

is a character.

But:

```java
"orders"
```

is a String.

Therefore:

```java
@Table(name = "orders")    // CORRECT
```

and:

```java
@Table(name = 'orders')    // WRONG
```

The error:

```text
Invalid character constant
```

occurs because Java interprets `'orders'` as a character constant, but a character constant can contain only one character.

Correct:

```java
@Table(name = "orders")
```

# 14. Can we provide more than `Order, Long`?

`JpaRepository` itself expects two generic parameters:



```java

        extends JpaRepository<Order, Long> {

    List<Order> findByCustomerName(String customerName);
```

# 37. Why don't we use `@Autowired` on the constructor?

Because there is only **one constructor**.

Example:

```java
@Service

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

Spring sees one constructor and understands:

> This is the constructor to use when creating the bean.

So:

```java
@Autowired
```

is unnecessary.

# 38. Can we use `@Autowired` on the constructor?

Yes.

This is valid:

```java

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
```

# 39. What if there are multiple constructors?

Suppose:

```java
@Service
public class OrderService {

    public OrderService() {
    }

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

Now Spring has multiple constructors.

It needs to know which one to use.

We can explicitly mark one:

```java
@Autowired
public OrderService(OrderRepository orderRepository) {
    this.orderRepository = orderRepository;
}
```

Now Spring knows which constructor should be used for dependency injection.

# 40. Why do we use `final`?

We write:

```java
private final OrderRepository orderRepository;
```

`final` means that once the field is initialized, it cannot be assigned another value.

Constructor:

```java
public OrderService(OrderRepository orderRepository) {
    this.orderRepository = orderRepository;
}
```

After initialization, we cannot do:

```java
this.orderRepository = anotherRepository;
```

This makes required dependencies explicit and helps keep the object properly initialized.

---

# 41. Why is constructor injection preferred?

Constructor injection has several advantages:

### 1. Required dependencies are explicit

The constructor tells us:

```java
public OrderService(OrderRepository orderRepository)
```

This class cannot properly be created without its repository.

### 2. Fields can be `final`

```java
private final OrderRepository orderRepository;
```

### 3. Easier unit testing

We can construct the service directly:

```java
OrderRepository mockRepository = ...;

OrderService service =
        new OrderService(mockRepository);
```

### 4. No hidden dependency

With field injection, the dependency is hidden inside the class.

With constructor injection, the dependency is clearly visible.

---

## Q6. What does `orElseThrow()` do?

**Answer:**

It returns the value contained in the `Optional` if present. If the Optional is empty, it executes the supplied exception-producing lambda and throws the resulting exception.

---

## Q7. What does this mean?

```java
() -> new RuntimeException("Order not found")
```

**Answer:**

It is a lambda expression. It provides the code that should be executed to create the exception when `orElseThrow()` needs to throw one.

---

## Q8. Why don't we use `@Autowired` in constructor injection?

**Answer:**

When a Spring bean has only one constructor, Spring automatically uses that constructor for dependency injection, so `@Autowired` is not required.

---

## Q9. Why is constructor injection preferred?

**Answer:**

It makes required dependencies explicit, allows dependencies to be declared `final`, makes classes easier to test, and avoids hidden field-based dependencies.

---

## Q10. Why does `@Table(name = "orders")` use double quotes?

**Answer:**

Because Java Strings use double quotes.

```java
"orders"
```

is a String.

Single quotes represent a single character:

```java
'o'
```

Therefore:

```java
@Table(name = "orders")
```

is correct.

# 51. The Most Important Mental Model

When you look at this:

```java
@Service
public class OrderService {

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    public Order getOrder(Long id) {

        return orderRepository.findById(id)
                .orElseThrow(() ->
                        new RuntimeException(
                                "Order not found: " + id));
    }
}
```

read it from top to bottom:

```text
@Service
   ↓
Spring manages OrderService
   ↓
OrderService needs OrderRepository
   ↓
Spring injects repository through constructor
   ↓
getOrder(id) is called
   ↓
repository searches database
   ↓
findById() returns Optional<Order>
   ↓
Order exists?
   |
   ├── YES → return Order
   |
   └── NO → orElseThrow()
                 ↓
             exception
```

And the repository:

```java
public interface OrderRepository
        extends JpaRepository<Order, Long> {
}
```

means:

```text
Spring Data JPA
      ↓
Repository for Order
      ↓
Order's ID is Long
      ↓
Automatically provides CRUD methods
      ↓
Communicates with database through JPA/Hibernate
```

This is the **core foundation of our Order Service**. Once this flow is clear, the next concepts—DTOs, validation, global exception handling, pagination, Spring Security/JWT, transactions, and database optimization—become much easier to understand.
